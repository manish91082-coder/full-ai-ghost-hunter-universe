# MACRO-BATCH EXECUTION DOCTRINE v1.0

## Objective
Measure progress by verified capability completed, not by number of chat turns or micro-files.

## Default execution unit
A Macro-Batch contains all logically related work that can be completed safely without waiting for a genuine external dependency or human authorization.

## Internal loop
1. Define macro objective.
2. Partition independent work.
3. Research in parallel.
4. Normalize and deduplicate.
5. Cross-check primary evidence.
6. Verify critical state.
7. Test.
8. Audit.
9. Discover material gaps.
10. Expand research for resolvable gaps.
11. Integrate.
12. Re-test.
13. Re-audit.
14. Saturation check.
15. Freeze and version.
16. Update durable control state.
17. Return one integrated result.

## Interaction minimization
The user should normally need one next command per meaningful macro-batch, not one command per subtask.

## Phase minimization
Multiple related roadmap domains may be completed together when dependencies permit. Documentation compression is allowed. Verification shortcuts are not.

## Artifact policy
Every material macro-batch produces a substantive batch artifact and audit artifact, and synchronizes PROJECT_STATUS, PROJECT_MEMORY where decisions changed, PROJECT_DETAILS where specifications changed, and PROJECT_LOG.

## Anti-drift
Every macro-batch records objective, current state, completed capability, remaining blockers, final-goal alignment and next macro objective.

## Safety
Fail-closed, zero-trust, live trading STOP until readiness gates pass, and expected net profit must exceed USD 0.20 after applicable measured costs. No execution on uncertain economics, stale critical data, failed simulation, insufficient liquidity or unresolved security risk.


## DATA UPDATE DISCIPLINE

Every macro-batch must distinguish **delta discovery** from **current-state materialization**.

New information is not automatically a new record. The mandatory sequence is: capture evidence → normalize → identity resolution → deduplicate → merge into current canonical state → preserve provenance → test → audit.

Macro-batch artifacts must not copy entire registries. They record deltas, coverage changes, conflicts, tests and audit results. Ordinary registry evolution updates the canonical file in place; Git history supplies historical versions.

Before beginning a new batch, duplicate/identity anomalies in the current canonical state are checked so accumulated duplication cannot silently propagate into later execution phases.
